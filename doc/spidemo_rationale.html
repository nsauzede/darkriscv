Rationale

Why this project

The starting point

A software background and some VHDL, but no Verilog yet.

The goal was a career move towards hardware: digital design, FPGAs, bare-metal software, and the serial buses that embedded boards run on, SPI and I2C.

The vehicle

DarkRISCV is a RISC-V core by Marcelo Samsoniuk, started in 2018 and "implemented from scratch in one night". It has about 2,600 stars on GitHub.

The whole stack fits in one repository: the Verilog core, caches, bus bridge, UART and I/O block, a boot.S, a tiny C library, a shell, an Icarus Verilog simulation and build files for about 20 boards. It is small enough to read end to end, and real enough that a maintainer reviews every change.

The approach

The history shows a deliberate climb. Each step needed the one before.

  1. Read and fix. Small bugs found by reading the core.
  2. Make it reproducible. A firmware build that works and a CI.
  3. Real boards. Two new FPGA ports.
  4. A new peripheral. SPI, to read a real accelerometer.
  5. Better tools. Sensor stubs and a Verilator cosimulation.

Under the hood

Four case studies

Each one is a small, real piece of digital design or embedded software, with the code that went upstream.

Case 1 · PR #76 · February 9, 2025

One character in the decoder

The core decodes each instruction's opcode into one-bit flags: XRCC for register-register operations, XCUS for the custom opcode, and so on. When the pipeline stalls, the input HLT is high and every flag must keep its own value until the stall ends.

One line kept the wrong value: during a stall, the custom-instruction flag was loaded with the register-op flag. It was found by reading the code next to its neighbours, not by a failing test. The PR said only "Seems like a copypasta ?".

In RTL a copy-paste error is silent. Reading each line against the lines around it is a real verification technique.

// rtl/darkriscv.v, execute stage
XRCC   <= HLT ? XRCC   : IDATAX[6:0]==`RCC;
- XCUS   <= HLT ? XRCC   : IDATAX[6:0]==`CUS;+ XCUS   <= HLT ? XCUS   : IDATAX[6:0]==`CUS;XSYS   <= HLT ? XSYS   : IDATAX[6:0]==`SYS;
The maintainer's answer, the same day: "for sure yes! thanks for the fix!"
Case 2 · PRs #85 and #86 · March 2025

Byte lanes, and a register designed in review

A 32-bit bus carries four byte lanes, and the byte-enable signal XBE says which ones a store writes. A C store of one byte to the LED register wrote both of its bytes, so writing the low eight LEDs also overwrote the high eight. The fix honours the byte enable.

The first version of the SPI block also depended on the access width: it answered with a different layout for each one. In review, the maintainer suggested one 32-bit word with control or status on top and data below, read and written whole. The merged register follows that advice.

A register map is an interface. Make it boring: one width, one layout, status where software can poll it.

// rtl/darkio.v, LED register write
- 5'b01000: LEDFF <= XATAI[15:0];+ 5'b01000: LEDFF <= XBE == 4'b0001 ? {LEDFF[15:8], XATAI[7:0]}+                                    : XATAI[15:0];
darkspi, at DarkIO offset 0x1C (address 0x4000001C)
write 31–240x00, or non-zero to configure the master 23–16command: register, read bit, auto-increment 15–0data to send, or a placeholder for the answer
read 31–24status: bit 25 ready, bit 24 busy 23–160x00 15–0data received, bytes swapped 
// read OUT_X_L and OUT_X_H in one 24-bit transfer: 0xE8 = 0x28 | read | auto-increment
*((volatile int *)SPI_MMADDR) = 0x00e80000;
short swapped_out_x = *((volatile short *)SPI_MMADDR);   // 0xLOHI

Case 3 · PRs #86, #89 and #92 · March and April 2025

SPI, one bit at a time

The LIS3DH accelerometer on the MAX1000 answers its WHO_AM_I register, 0x0F, with 0x33. Reading it takes 16 clock cycles: eight command bits out on SDI, eight data bits back on SDO. The sensor uses SPI mode 3, so the clock rests high and both sides sample on the rising edge. The diagram is the exchange as written by hand in src/spidemo/SPIBB.md.

Datasheet limits noted in SPIBB.md: clock period 100 ns minimum (10 MHz), chip-select setup 5 ns and hold 20 ns, SDI setup 5 ns and hold 15 ns, SDO valid within 50 ns.

Having both made it possible to check one against the other on the real sensor. 3-wire SPI came next: one pin carries data both ways, so the master must release it, put it in high impedance, before the sensor answers.

Bit-banging from a PC, through the UART

The helper ser.py sends shell commands over the serial port. Each hex digit of a bb command is one write of four pins: enable, chip select, clock, data.

./ser.py "set_bb 1" "bb 7 f b 9 b 8 a 8 a 8 a 9 b 9 b 9 b 9 b ..."
#  f = 1111  idle: CS high, clock high
#  9 = 1001  CS low, clock low,  data 1
#  b = 1011  CS low, clock high, data 1   ("9 b" clocks out a 1)
#  8 = 1000  CS low, clock low,  data 0
#  a = 1010  CS low, clock high, data 0   ("8 a" clocks out a 0)

A protocol is learned at the bit level. Drawing one transaction by hand, then making two independent implementations agree, is how the datasheet becomes real.

Case 4 · PR #90 · March 31, 2025

Watching the SoC from a window

Icarus Verilog interprets the design and writes waveforms. Verilator takes another route: it compiles the Verilog into a C++ model that a program can step. sim/Vdarksocv_gui.cpp wraps that model in an ImGui window with Run, Step, AutoStep and Reset buttons, a clock checkbox and the LED register.

Running the same RTL through two simulators also catches code one of them tolerates. The cost showed at once: serial output through the C++ model was so slow that a NOBANNER option was added to skip the boot banner.

A simulator is a tool you can build on. A cosimulation turns the RTL into a library you drive from your own code.

# sim/README.md
make clean all APPLICATION=spidemo NOBANNER=1 SPIBB=1 COSIM=1

// sim/Vdarksocv_gui.cpp, the control strip
ImGui::Checkbox("Run", &run);
ImGui::SameLine(); if (ImGui::Button("Step")) { step = 2; }
ImGui::SliderInt("StepTime", &step_time, 1, 10);
ImGui::Checkbox("clk", &clk);
ImGui::SameLine(); if (ImGui::Button("Reset")) { reset = true; }
ImGui::Text("LED %08lX", (unsigned long)darksocv->LED);
Collaboration

What review taught

Every pull request went through the maintainer. The threads are public, and four of them carry lessons that apply to any team.

#75 · Add GitHub Actions CI

One concern per pull request

The first version bundled the CI with a whitespace cleanup. The maintainer welcomed the CI but asked for the cleanup in separate pull requests, being unsure about it. The PR was trimmed to the CI alone, and #77 and #78 followed.

#78 · Remove trailing spaces, 90 files

History is worth more than tidiness

"we will change lots of files, including some that were not changed for a long time, which may disrupt the sense of time on such files"
The maintainer

A mass reformat makes every old file look recently touched and buries its real history under one commit. Nicolas agreed and closed the PR.

#86 · Add darkspi SPI master · RFC

Ask early, and say it is a draft

Marked as a request for comments, the first SPI version got two detailed reviews: let the bus bridge route the bytes, use one 32-bit register, move the SPI files into rtl/lib/spi, state the license clearly. The second version was rewritten around them and tested on the MAX1000. Before merging, the maintainer built it for another board with Xilinx ISE.

"always remember test the case where everything is disabled, just to ensure the basic scenarios are working!"
The maintainer, in the same review
#80 · MAX1000 port

Good structure gets noticed

The port gave the board its own top.v, so board-specific parts such as the PLL and RAM stay out of the shared SoC. The maintainer replied with plans for exactly that structure on every board, so that one day several cores could be mapped onto one chip.

Honest accounting

Dead ends and open threads

Fourteen of the 35 commits never landed. Most were experiments by design. A few are worth keeping in mind.

Left as work in progress

Upstream moved the ground

On May 23 the maintainer made big-endian the default. In June the spidemo branch fell back to little-endian with bit-banging disabled and marked broken, and a fix attempt stalled. On July 2 upstream went back to little-endian. Nothing in the CI ran the spidemo, so the break had to be found by hand.

A feature that no automated test runs belongs to whoever changes the code next.

Branch

I2C never landed

Two branches: I2C by bit-banging, an I2C master in Verilog, and a stub of the sensor answering on I2C. The notes draw a complete WHO_AM_I exchange: start, address, acknowledge, repeated start, stop. The last I2C commit came the day after the final SPI merge.

A clean end point matters. Half a protocol is hard to pick up again.

Branch

Old boards, old tools

Reviving the Papilio and Spartan-3 boards meant Xilinx ISE, a toolchain frozen since 2013. The ADXL345 stub for the DE10-Nano and a UART queue for simulation stayed on branches too.

Vendor tools set the pace of FPGA work, often more than the design does.

Known limit

Cosimulation is slow

The README says it plainly: performance "is not as good as expected, for now". Printing over the simulated UART costs so much that the banner had to become optional.

Measure where simulated time goes before adding features to a simulator.

Found in the October 2026 audit

The CI checks the build, not the behaviour

The simulation ends with $finish both at the shell prompt and on an invalid instruction, and both exit with status 0. On the June 2025 branch the job would pass even though the core cannot boot its committed image, built big-endian for a little-endian core.

Make every test fail once on purpose. A check that cannot fail checks nothing.

Fit

A small FPGA pushes back

On the MAX10 the generic RAM would not map to block RAM. The choice was a read-modify-write workaround or a board-specific wrapper around Intel's altsyncram. The PR took the wrapper and named the cleaner fix as future work.

Portable Verilog meets vendor primitives at the memory. Plan for it.

Try it

The default simulation needs only Icarus Verilog: it boots the firmware shipped in the repository and stops at the shell prompt. Rebuilding the firmware needs a RISC-V cross compiler, whose prefix and directory go in CROSS and CCPATH.

Then open the waveform in GTKWave and look for SPI transfers like the one in the diagram above.

git clone https://github.com/darklife/darkriscv
cd darkriscv
make                                  # simulate the shipped firmware
make clean all APPLICATION=spidemo    # rebuild with SPI, simulate
gtkwave rtl/lib/spi/darksocv.gtkw
